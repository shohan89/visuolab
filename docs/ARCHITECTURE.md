# Visuolab — Production Architecture

Status: design only. No dashboard code and no content migration exists yet. Basis: `docs/EXISTING-SITE-AUDIT.md`.

## 0. Principles and decisions

1. **The static site is the visual source of truth.** The public site keeps the six original CSS files byte-for-byte, in the original order, and applies to each route only the sheets the static page originally loaded (`StyleGate`, see `DESIGN-PARITY.md`) because the files reuse class names such as `.out` and `.about-lead` with different meanings. JSX reproduces the original DOM class for class. A screenshot diff against the static site gates every public page.
2. **Server Components by default.** Public pages are server-rendered markup from D1. Client Components exist only where the audit found real interaction (section 4).
3. **Content is data, structure is code.** Page structure, section order, icons and SVG art stay in code. Copy, lists, numbers, images and SEO fields come from D1 and R2.
4. **One Worker.** Public site, admin and API run in one Cloudflare Worker built with **vinext** (Cloudflare's Vite-based Next.js runtime, `vinext` + `@vinext/cloudflare`) and configured through Wrangler. One deploy, one set of bindings.
5. **Every claim that depends on an adapter or framework version is marked "verify".** These are spikes in Phase 0 of the plan (section 15), not assumptions.

Decisions made here that update earlier notes:

| Topic | Decision | Reason |
|---|---|---|
| Password hashing | PBKDF2-SHA256 through WebCrypto (100,000 iterations), not scrypt | Native and fast on Workers. `scrypt` in `node:crypto` is pure CPU time. `scripts/hash-password.mjs` must be changed to PBKDF2 before use. |
| `/services` | Route exists but **redirects (308) to `/#services`** | The original site has no services overview page. The nav item is a button that only opens the mega menu. Building a listing page would invent new UI. |
| Rich text | Tiptap, stored as JSON, rendered by an allow-list React renderer | No raw HTML stored or injected. Output maps to the existing `.prose` styles. |
| Images | Plain `<img>` with pre-sized WebP, served from R2 | Keeps crops, `object-position` and sizes identical. `next/image` optimizer is not used. Cloudflare Images transforms are an optional later step. |
| Middleware | Auth is enforced in a data access layer on the server. `proxy.ts` (Next 16 name for middleware) is only an optimistic redirect | Never trust the redirect layer alone (section 6). Verify vinext supports `proxy.ts` on the installed versions. |

- Unknown or unpublished slugs call `notFound()`.
- In-page links from the original (`index.html#process`) become `/#process`. `SiteMotion` handles hash arrival on any page.

## 4. Server/client boundaries

### 4.1 What stays on the server

All page sections and all copy. Specifically (decided from the audit):

- The manifesto is split into `<span class="w">` words **on the server** in JSX. The client only writes a `--o` CSS variable per word.
- Article headings get ids generated at render time. The TOC list is also built at render time. Only the scroll-spy highlight is client code.
- Share links are rendered on the server from the canonical URL. Only the copy-link button is a client component.
- Clock cities, flags and time zones render on the server with `--:--` placeholders (as the HTML does). Ticking is client.
- Filter chip counts and card `data-tags` come from data.

### 4.2 Client components

| Client component | Behavior (audit reference) | Props / source |
|---|---|---|
| `SiteMotion` (mounted once in `(site)/layout.tsx`) | Lenis, anchor easing, hash arrival, load-in class, nav `.scrolled` / `.over-light`, `.reveal` IntersectionObserver, case-stack `--p`, showreel `--p` + video play/pause, manifesto `--o`, the shared scroll driver | none; re-initialises on `pathname` change with full cleanup |
| `HeroController` | `hero.js` behavior (scroll progress, parallax, stars) | ref to `.banner` |
| `MeshCanvas` | `mesh.js` WebGL shader | ref to `.mesh` |
| `AboutScene` | `scene.js`, loaded with `next/dynamic` (`ssr:false`), `/about` only | none |
| `MobileNav` | dialog, focus trap, Lenis stop/start | nav data |
| `FilterGrid` (wraps works and blog grids) | chip state, `.is-hidden`, empty state | items + chips |
| `Faq`, `Stairs` | accordion and tooltip state | items |
| `Clocks` | 1s ticker, `Intl.DateTimeFormat` | offices |
| `CarouselButtons` | `scrollBy` on `#carousel` | target id |
| `TocSpy`, `CopyLink` | scroll-spy, clipboard | heading ids |
| `ContactForm`, `NewsletterForm` | submit through server actions, validation, success state | action |

Approach for the scroll-linked effects: `SiteMotion` ports `main.js` logic into typed modules in `lib/motion/` that query the same DOM (`.reveal`, `.case-panel`, `.reel`, `[data-scroll-words]`, `.light`). This keeps the server-rendered markup identical to the original, and avoids hundreds of tiny client wrappers. Each module exports `init(): () => void` (cleanup). `SiteMotion` calls them in a `useEffect` keyed on `pathname`.

Reveal fallback: add a `<noscript><style>.reveal{opacity:1;transform:none}</style></noscript>` in the site layout. This is the only intentional change (it only affects no-JS users).

### 4.3 Rules

- A Client Component never imports from `lib/db`, `lib/auth` or `lib/mail`.
- Props passed to client components are plain serializable data only.
- Three.js, Lenis and the shader modules are imported only inside client files. Three.js loads only on `/about`.

## 5. Database architecture (D1 + Drizzle)

D1 is SQLite. Use Drizzle ORM and `drizzle-kit generate` for migrations. `wrangler d1 migrations apply` runs them. Writes that span tables use `db.batch([...])` (D1 has no interactive transactions).

### 5.1 Modelling approach

- **Entities that have URLs, lifecycle or are queried independently** are rows: services, cases, posts, testimonials, authors, media.
- **Ordered, repeatable fields owned by one parent** (a case's 4 phases, 3 challenges, 6 results, gallery, a service's 4 overview blocks and 6 included items) are JSON columns validated by Zod. The admin edits them with repeatable-field editors. This avoids a dozen join tables for content that is always read and written together.
- **Site-wide lists** (FAQ, principles, milestones, offices, roles, industries, marquee logos, badges, nav items) are rows in a generic `content_items` table keyed by `collection`, ordered by `position`. They are small, always fetched by collection and need drag-to-reorder.

Statuses: `draft | published | scheduled | archived`. Scheduled publish is evaluated at read time (`published_at <= now`) and a Cron Trigger (every 10 min) calls `revalidateTag` for items that just went live.

### 5.3 Data access

- `lib/db/queries/*.ts` is the only place that touches SQL. Pages and actions call these functions. Each returns plain objects typed from Drizzle.
- Public read functions are cached (section 11). Admin reads are never cached.
- Zod schemas in `lib/validation` define every JSON column; they run on write and on import. Reads trust the data but pass through a tolerant parser with defaults so one bad row cannot crash a page.

## 6. Authentication architecture

Scope: one admin login at `/admin/login` (email + password). Custom sessions, no third-party auth library.

- **Credentials:** `admin_users` row created by a one-off seed script from the `ADMIN_EMAIL` var and an `ADMIN_PASSWORD_HASH` secret. Hash format: `pbkdf2$sha256$100000$<salt b64>$<hash b64>`. Constant-time compare. The password is never stored or logged.
- **Session:** on login, generate 32 random bytes, store `SHA-256(token)` in `sessions`, set cookie `__Host-vl_session` with `HttpOnly; Secure; SameSite=Lax; Path=/`. Idle expiry 12 h (sliding), absolute 14 days. Logout deletes the row. Changing the password revokes all sessions.
- **Rate limiting:** `login_attempts` keyed by hashed IP and by email. 5 failures in 15 minutes locks that key for 15 minutes. Same generic error for wrong email and wrong password. A fixed minimum response time avoids user enumeration by timing.
- **Optional hardening:** Turnstile on login after 3 failures; TOTP second factor (`admin_users.totp_secret`) is a planned extension, not v1.
- **Enforcement (defence in depth):**
  1. `proxy.ts` redirects unauthenticated `/admin/*` requests to `/admin/login` (UX only).
  2. `lib/auth/guard.ts` exports `requireAdmin()`. It is called in the `(console)/layout.tsx` **and** at the top of every admin server action and admin route handler. Data functions for admin writes take the verified user as a parameter.
  3. Cookies are read only on the server.
- **CSRF:** Server Actions get Next's origin check. Route handlers (media upload) require a same-origin `Origin` header and a custom header `x-vl-csrf` matching a per-session token delivered in the admin layout.
- **Login page** has no link from the public site and `noindex`.

## 7. Media architecture

- **Storage:** R2 bucket `visuolab-media`, binding `MEDIA`. Keys are content-hashed: `m/<sha256-12>/<slug>.<ext>`. Hashed keys are immutable, so responses can be cached for a year.
- **Upload flow:** admin form → `POST /api/admin/media` (auth + CSRF) → validate (size, MIME by magic bytes, extension, image dimensions) → stream to R2 → insert `media` row → return id and URL. Allowed: `image/webp`, `image/jpeg`, `image/png`, `image/avif`, `video/mp4`. **SVG uploads are rejected** in v1 (script risk). Limits: images 5 MB, video 50 MB (Worker request limit applies; larger files would need multipart upload, deferred).
- **Delivery:** `GET /media/[...key]` reads R2 and returns the object with `Content-Type`, `ETag`, `Cache-Control: public, max-age=31536000, immutable`, and `Accept-Ranges` plus 206 responses for video (needed for `<video>`). Cloudflare's CDN caches it. A custom domain on the bucket (for example `media.<domain>`) can replace this route later without changing stored keys.
- **Image sizing:** the original uses fixed WebP files and `object-position` crops. Uploads are expected to be pre-sized WebP (admin warns above recommended dimensions). Focal point (`focal_x/y`) is stored and rendered as `object-position`, so crops are editable. If responsive variants are needed later, enable Cloudflare Image Transformations on the zone and add a `cdnImage(url, {width})` helper; no schema change.
- **Existing assets:** the 28 files in `public/assets` stay in the repo (served by the Worker's static assets) and are registered in `media` with `source:'static'` and their original paths. Content migration later copies chosen files into R2 and updates references. Nothing is deleted from the reference site.
- **Alt text:** required field in admin for images used as content. Decorative images are marked as such (empty `alt`).
- **Deleting media** is blocked while a row references it (checked across `cases.gallery`, `services`, `posts`, `testimonials`, `authors`, `seo`, `settings`).

## 8. Admin dashboard architecture

Separate root layout, own `admin.css` (neutral UI; it does not need to match the public design). No public CSS is loaded there.

```
components/admin/
├─ shell/        AdminShell, Sidebar, Topbar, UserMenu, Toaster
├─ data/         DataTable (server-paginated), StatusBadge, EmptyState, ConfirmDialog
├─ forms/        FormField, TextField, SlugField, SelectField, SwitchField,
│                MediaPicker, SeoPanel, RichTextEditor (Tiptap), RepeaterField, RepeaterItem, SortableList
└─ editors/      ServiceForm, CaseForm, PostForm, SettingsForms, NavEditor, ContentItemsEditor
```

- **Pattern per entity:** list page (server component, search, status filter, pagination via `searchParams`) → `new` and `[id]` pages render one shared form component → the form is a client component that calls a server action. Validation runs with the same Zod schema on client and server.
- **Repeaters:** phases, challenges, results, gallery, overview blocks, included items, outcomes, FAQ and similar. Drag-to-reorder (`@dnd-kit`), add/remove, per-item validation.
- **Rich text:** Tiptap with a restricted extension set matching `.prose` styles (headings h2/h3, paragraph, bold, italic, link, lists, blockquote, hr, image from media library). Output JSON is validated against an allow-list schema on save.
- **Draft/publish:** status field, scheduled date, "Preview" opens the public route with a signed preview cookie (`draftMode`) so unpublished items render with the real design.
- **Concurrency:** each row has `updated_at`; forms send it back and the action rejects stale saves with a clear message.
- **Submissions:** table with status changes, notes, CSV export, delete. Unread count in the sidebar.
- **Navigation:** `/admin/navigation` has two sections, HEADER NAVIGATION (primary links, contact button, Services dropdown columns, cards and promo) and FOOTER NAVIGATION (link columns). The page is a server component; `NavigationEditor` (client) holds the draft, `saveNavigation` (`src/actions/navigation.ts`) checks the origin, requires the admin role, validates the whole section and saves it atomically (see `DATABASE.md` section 7). The public header and footer read the same table (`NavigationProvider`); their markup is unchanged.
- **Settings tabs:** Site facts, SEO defaults and per-static-page SEO, Home blocks, About blocks.
- **Audit:** every write adds an `audit_log` row.
- **Admin UI library:** any accessible component set may be used here (the public design rule does not apply). Keep it out of the public bundle by only importing it under `(admin)`.

## 9. API / server action architecture

Prefer Server Actions for form posts and mutations; use Route Handlers only where a raw HTTP interface is needed (file upload, streaming, health, R2 reads).

### 9.1 Public

| Name | Type | Input | Behavior |
|---|---|---|---|
| `submitContact` | Server Action | `name`, `email`, `company?`, `needs[]`, `budget?`, `message` (+ honeypot, Turnstile token) | Zod validate → verify Turnstile → rate-limit by IP hash (e.g. 5/hour) → insert `submissions` → `after()` send Resend notification to `MAIL_TO` and update `notified_at` / `notify_error`. Returns `{ok}` or field errors. UI state matches the original `.form-ok`. |
| `subscribeNewsletter` | Server Action | `email` (+ Turnstile) | Validate, rate-limit, upsert `subscribers`. Returns a generic success so existing addresses are not revealed. |
| `GET /media/[...key]` | Route Handler | key | R2 read (section 7). |
| `GET /api/health` | Route Handler | none | Checks D1 and R2 bindings, returns status only. |

### 9.2 Admin (all call `requireAdmin()` first, validate with Zod, write `audit_log`, then `revalidateTag`)

- Auth: `login`, `logout`, `changePassword`.
- Services, cases, posts: `create`, `update`, `setStatus`, `reorder`, `delete`, `duplicate`.
- Content items and nav: `saveCollection(collection, items[])`, `reorder`.
- Settings and integrations: `saveSettings(group, data)`, `sendTestEmail`.
- Submissions: `setSubmissionStatus`, `deleteSubmissions`, `exportSubmissionsCsv` (route handler, streams CSV).
- Media: `POST /api/admin/media` (upload), `updateMedia` (alt, focal), `deleteMedia`.

Conventions: actions return `{ ok: true, data } | { ok: false, error, fieldErrors? }`; never throw to the client for validation errors; log server errors with a request id.

## 10. SEO architecture

- **Metadata:** each page exports `generateMetadata()` using `lib/seo/metadata.ts`. Order of precedence: entity `seo` row → entity fields (title, excerpt) → page default in `settings` → site default. Output title, description, canonical, robots, Open Graph, Twitter card, and `og:image` from the cover media. Title templates preserve the original format (`<Page> — Visuolab`).
- **Existing titles and descriptions** from the 23 static pages are the seed values, so SEO text does not change at launch.
- **Canonical host:** one canonical origin from `SITE_URL`. Redirect all other hosts to it.
- **`sitemap.ts`:** static routes + published services, cases, posts with `lastmod` from `updated_at`. Excludes `/services`, admin, drafts.
- **`robots.ts`:** allow all public paths; disallow `/admin` and `/api`; reference the sitemap.
- **Structured data (JSON-LD):** `Organization` and `WebSite` on all pages; `BreadcrumbList` on detail pages; `Article` on posts; `Service` on service pages; `CreativeWork` on cases; `ContactPage` on contact. Rendered server-side in a `<script type="application/ld+json">` with escaped content.
- **Redirects:** legacy `.html` URLs (config) and slug changes (`redirects` table) return 308.
- **Performance signals:** LCP images (`earth.webp`, hands, case covers above the fold) keep `fetchpriority="high"`; below-fold images keep `loading="lazy"`; images keep `width`/`height` to avoid layout shift. Fonts keep `preconnect` and `display=swap`.
- **No-JS content:** server markup contains all content. Only the `.reveal` start state hides it, handled by the `<noscript>` rule.
- **Admin and API:** `X-Robots-Tag: noindex` header and `robots` meta.
- **Favicon / OG default image:** missing from the original; added as assets without touching layout.

## 11. Caching strategy

Goal: public pages are served from cache and never wait on D1; edits appear within seconds.

**Default design (ISR with tags), verify on the installed vinext version:**

- Public pages are statically generated (`generateStaticParams` for slugs) and revalidated **on demand**: `revalidateTag()` / `revalidatePath()` from admin actions. Tags: `settings`, `nav`, `services`, `service:<slug>`, `cases`, `case:<slug>`, `posts`, `post:<slug>`, `testimonials`, `content:<collection>`, `media`.
- Public data functions are wrapped in a cache primitive with those tags. D1 queries are not `fetch`, so use `unstable_cache` (or Next 16 `'use cache'` + `cacheTag` if Cache Components is enabled — choose in the Phase 0 spike).
- vinext cache adapters (declared in `vite.config.ts`): `kvDataAdapter()` for the `"use cache"` data cache (KV namespace), and a CDN adapter (`workersCacheCdnAdapter()`, `staticAssetsAdapter()` or `responseStoreAdapter()`) for page-level ISR. `revalidateTag()` / `revalidatePath()` purge them. The base project currently uses no cache adapter (`--cdn-cache=none --data-cache=none`); choose in the Phase 0 spike. vinext documents `"use cache"` / Cache Components as only partially implemented, so prefer `unstable_cache` + tags unless the spike proves otherwise.
- A safety `revalidate` of 1 hour on public pages covers missed invalidations; a Cron Trigger revalidates scheduled publishes.
- Dynamic and never cached: `/admin/*`, server actions, `/api/*`, preview (`draftMode`).
- Static asset and media headers: `/media/*` and `/assets/*` `immutable` for hashed keys; original static assets use a long max-age with versioned filenames.
- Fonts and third-party scripts: Lenis and Three.js are bundled, not loaded from jsDelivr (removes a third-party runtime dependency; the original loaded them from the CDN).

**Fallback if the spike shows ISR on Workers is unreliable:** render pages dynamically on the Worker and cache the HTML at the edge with the Cache API, purging by URL list from admin actions. Same tags, different storage. The data layer and route structure do not change.

- **Already provisioned** (Visuolab account `48fa30c6…e01`): D1 `visuolab` (`09818a92-a4b7-4ec1-a009-740b8e353402`), R2 `visuolab-media`. `wrangler.jsonc` has `account_id`, bindings `DB`, `MEDIA`, flags `nodejs_compat` and `global_fetch_strictly_public`.

- **Domain and edge:** custom domain attached to the Worker. TLS full-strict, HTTP→HTTPS, HSTS. WAF managed rules and a rate-limit rule on `/admin/login` and the form actions.

## 14. Security model

**Threats and controls**

| Area | Control |
|---|---|
| Authentication | PBKDF2-SHA256 600k; opaque random session tokens, only hashes stored; `__Host-` cookie, HttpOnly, Secure, SameSite=Lax; idle and absolute expiry; revoke on password change; login rate limit and lockout; generic errors; optional TOTP later |
| Authorization | `requireAdmin()` in every admin layout, action and handler; no reliance on `proxy.ts` alone; single role now, `role` column ready |
| CSRF | Server Action origin check; route handlers verify `Origin` and a per-session token header; SameSite cookies |
| XSS | React escaping by default; **no `dangerouslySetInnerHTML` for user content**; rich text rendered through an allow-list renderer (node types, marks, link protocols `http/https/mailto`); JSON-LD escaped; admin inputs trimmed and length-limited |
| Injection | Drizzle parameterized queries only; no string-built SQL; Zod on every input |
| Uploads | Auth + CSRF; size limits; MIME sniffing by magic bytes; extension allow-list; no SVG; random hashed keys; files served with `Content-Type` and `X-Content-Type-Options: nosniff`; `Content-Disposition` for non-image files |
| Forms / spam | Turnstile, honeypot field, time-to-submit check, per-IP hash rate limit, max field lengths, email format validation; IP stored only as a salted hash |
| Email | Header injection prevented by passing fields only as data to Resend; HTML escaped in templates; notification failure is logged and shown in admin, not exposed to the visitor |
| Headers (set in `next.config.ts` / worker) | `Content-Security-Policy` (self, fonts.googleapis.com, fonts.gstatic.com, Turnstile origin, `img-src 'self' data:`, `media-src 'self'`; nonces for the JSON-LD and inline styles where needed — the original uses inline `style` attributes, so `style-src` needs `'unsafe-inline'` unless refactored), `Strict-Transport-Security`, `X-Content-Type-Options`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy`, `X-Frame-Options: DENY` (`frame-ancestors 'none'`) |
| Secrets | Worker secrets only; none in the repo, bundle or logs; separate tokens for CI with minimum scopes (Workers Scripts, D1, R2 edit on this account only) |
| Data privacy | Submissions contain personal data: retention setting (default delete after 24 months), export and delete in admin, no analytics cookies, mention in privacy policy |
| Supply chain | Lockfile committed, `npm audit` in CI, Dependabot, no runtime CDN scripts (Lenis and Three.js bundled) |
| Availability | Edge caching of public pages; WAF rate rules; D1 and R2 backups; health endpoint |
| Auditability | `audit_log` for all admin writes; auth events logged |
| Preview / drafts | `draftMode` cookie signed with `SESSION_SECRET`, admin-only to enable |

**Residual items to decide:** whether to require TOTP for the admin before launch; retention period for submissions; whether newsletter needs double opt-in (depends on the audience and region).
